## What every component does

- **A name that is never a literal in the component.** Visible text, accessible names and descriptions come in as parameters, from a text key (`tr!`) or from the caller. `no_literals_in_render_code` in `src/i18n/tests.rs` scans every file under `src/ui/ds` for a literal handed to `.child(` or `aria_label(`, and `no_literal_names_descriptions_or_tooltips` does the same for `accessibility_label(`, `aria_description(`, `aria_value(`, `aria_placeholder(`, `tooltip(` and `Label::new(`, for the label or name handed to `Button::new`, the six kind constructors of `Button` (`Button::primary` and so on), `IconButton::new`, `Shortcut::from_keystroke`, `TextField::new` and `Switch::new`, for the text handed to `Chip::new`, `Chip::standalone`, `VaultBadge::team` and `VaultBadge::other`, for the name handed to `Tile::standalone`, `Chip::standalone`, a badge's `standalone` and `Standalone::new`, for the parts of a row's name handed to `RowParts::new` and to its `role_word`, `customer`, `client`, `user` and `vault`, for the sentence handed to `description()`, `note()` and `error()`, for the name handed to `SecretField::new`, and for the line handed to the footer's `connect_first` and the notes handed to `FooterTone::Offline`, `FooterTone::Tie` and `FooterTone::UpdateReady`. It reads the argument that carries the text, so an element id or the key string of a shortcut may still be a literal. Neither scan finds one. The only literals a component shows are keycap glyphs, the word "Esc", the twelve dots of a hidden secret, the six of a masked code, the symbol `s` after the seconds of the one-time code ring, and the punctuation between the parts of a row's name, of its second line and of the footer's description. The texts the components add themselves are text keys in `locales/a11y.yml`: `a11y.not_available` and `a11y.in_progress` on the button, `a11y.copy_password`, `a11y.reveal_password` and `a11y.hidden` on the secret field, `a11y.one_time_code_expires` on the ring and `a11y.more_actions` on the footer. Their tests write the English out instead of calling `tr!`, so each component is the only code that reads its keys, and `no_unused_keys` fails if a literal ever takes the place of one.
- **A name in every build.** A button, icon button, switch or text field with an empty name panics in its constructor, in release builds as well, because VoiceOver can only call such a control "button". So does a shortcut pair with an empty word, which would be keycaps alone, a chip without its text, a team badge or another vault's badge without its initial, a tile, a chip or a badge on its own without its name, and a secret field without its name.
- **A stable element id** as the first argument of the constructors of the button, the icon button, the text field, the switch, the row, the secret field, the one-time code ring and the panel footer; a shortcut pair writes no accessibility node and takes none. The button, the icon button, the text field, the row and the secret field also take an optional `AccessibilityId` through `.accessibility_id()`, the identifier assistive technology and UI tests see (`fp.<window>.<component>.<index>`). The switch takes none, because the Kit switch has no place for one (see Limits). An `AccessibilityId` is built from names fixed in the code and a number, so that no entry title, user name or host ends up in it. The type has a file of its own, `src/ui/ds/components/accessibility_id.rs`, and its field is private to that file: a tuple construction anywhere else, in the other components too, does not compile, and `AccessibilityId::new` is the only constructor. `new` is visible inside `ui::ds` only, so a call from `src/app`, from `examples/` or from anywhere else outside the design system does not compile either. It takes `&'static str` for the names, which keeps a borrowed title out but not a leaked one, since `Box::leak` turns any text into a `&'static str`. So `an_accessibility_id_takes_literal_names_only` reads the source: `new` is still visible inside `ui::ds` only, its names are still `&'static str`, and every call written `AccessibilityId::new` in a file under `src/ui/ds` passes string literals for both. The scan leaves out comments and inline test modules (`#[cfg(test)]` followed by `mod tests {`) up to their closing brace. String literals stay as they are, so the `//` in `"https://"` starts no comment, and code after a test module, or after a `mod tests;` that puts the tests in a file of their own, is read. The components keep the id as that type until they draw, and hand it to GPUI through `AccessibilityId::apply`, or `apply_to_input` for the GPUI Kit's input, both in the same file. GPUI's own `accessibility_id` takes any text, an entry title too, so `raw_accessibility_ids_are_applied_in_one_file` reads every other file under `src/ui/ds` the same way and fails for a call to a method of that name, whatever its receiver, or to `set_author_id`. What neither the compiler nor the tests see is under Limits.
- **Sizes in points at text size 13**, set with `u()`, so the larger text size (15) scales heights, spacing and text together. Radii, strokes and the focus ring stay in pixels.
- **One focus ring.** Focus from the keyboard shows a ring outside the control, 2 px in `focus.ring` with 1 px of space, which takes no room; focus from a click shows none. The button, the text field, the switch and the value of the secret field draw it with the same code, `src/ui/ds/components/focus_ring.rs`, and the text field and the switch turn the GPUI Kit's own ring off for it. One test helper checks it for all four (`the_focus_ring_shows_for_the_keyboard_only`, `the_text_field_shows_the_focus_ring_for_the_keyboard_only`, `the_switch_shows_the_focus_ring_for_the_keyboard_only`, `the_value_copies_from_the_keyboard_and_shows_the_focus_ring`), in a window where a button follows the control as a second tab stop. A key press while nothing has focus draws no ring. After Tab, focus adds one ring to the frame, around the control: its place comes from its bounds and its width from the edge GPUI paints, and focus may add no other edge, which is what the Kit's ring or a ring around a control without focus would paint. After Tab moves on to the button, the control has no ring, and after a click on the control there is none either. A row draws the ring inside its edge instead, where a list that scrolls cannot cut it off (see the row).

## The button

`Button` draws its own look on the unstyled `gpui_base::Button`, which brings focus, Tab, Space, Return and the accessibility role. GPUI Kit does not re-export it, so `gpui-base` is now a direct dependency, pinned at the 0.7.1 that `Cargo.lock` already had. Only the dependency list of `ferrispass` changed in `Cargo.lock`.

| Kind | Surface | Text | For |
|---|---|---|---|
| `Primary` | `button.primary.bg`, copper | `button.primary.text` | the action the view is for |
| `Secondary` | `button.secondary.bg` | `button.secondary.text` | other actions |
| `Quiet` | none until hovered | `button.quiet.text` | small, calm actions; also the icon button |
| `Ghost` | none until hovered | `button.ghost.text` | a verb inside a row |
| `Danger` | `button.danger.bg` | `button.danger.text` | anything that cannot be undone |
| `Large` | copper, as a capsule | `button.primary.text` | the lock screen and onboarding |

The sizes are 24, 28, 32 and the 44 capsule, which stays fully rounded at any text size. `Large` is a capsule by default, every other kind 28. The label is `Headline`.

- **States.** Under the pointer the surface takes the kind's hover color. Held down, the button fades to 0.72 instead of shrinking, because GPUI cannot scale an element. Keyboard focus draws the ring of every component outside the button; focus from a click shows none. A disabled button keeps its shape, takes `button.disabled.bg` and `button.disabled.text`, has no handler and is not focusable. A loading button keeps its label and its colors and takes no click, so like a disabled one it shows no pointing hand, no hover surface and no fade while held. It shows a spinner next to the label after 400 ms, so a quick action does not flash one; the delay is timed on GPUI's clock, which is the system clock in the app and a clock the tests can move. Until the spinner is due, the button asks for the next frame, so the spinner shows even when nothing else draws the window again. `a_loading_button_asks_for_frames_until_its_spinner_shows` draws the window only for the frames the button asks for.
- **VoiceOver.** The role is `Button`, or `DefaultButton` for the button Return presses (`default_button()`). The macOS adapter of AccessKit in `Cargo.lock` (0.26.3) hands `DefaultButton` to VoiceOver as a plain button (`accesskit_macos-0.26.3/src/node.rs:72`), so VoiceOver reads the default button like any other button today. The name is the label, so a label says what happens and to what. A description can add to it, such as "Production system"; a disabled button says "not available" there instead, because GPUI has no disabled flag for assistive technology yet, and a loading one "in progress". The keys of a shortcut go into `aria_keyshortcuts`, never into the name.
- **VoiceOver's press.** GPUI answers a press by clicking the middle of the button with a synthetic mouse, which misses when something covers the button. The button registers its own press, which calls the handler directly, as a click from the keyboard would.
- **The default button** shows the Return keycap unless it has a shortcut of its own, and puts ⏎ into `aria_keyshortcuts`. `default_button()` does not bind Return; the screen binds it, as it binds the keys of `shortcut()`. A danger button can never be it: Return never triggers something that cannot be undone. Asking for it fails in a debug build and leaves the button as it was in a release build. The debug check sits in a small module of its own, which a test can turn off for its thread, so `a_danger_button_never_becomes_the_default_button` builds `Button::danger(..).default_button()` in every build, runs it as a release build does, and reads the node the button draws. The role and its ⏎ keys live in a module of their own inside `button.rs`: the role's flag and the key string for Return are private there, and `make_default`, after the check, is the only code that builds them. Code anywhere else in the file cannot build the flag or name the key string, but it can copy both from a button that passed the check, or change the kind of a danger button around a call to `make_default`, and both compile. In the constructors, in `default_button`, in `make_default` or where the button is drawn, such code fails the test, which takes that path; in a builder method the test does not call, it is past every test (see Limits). `the_default_role_is_set_behind_its_guard_only` reads the source of the module: the flag stays private, `make_default` sets it after the check and is the only place in the module that builds or writes it, and the key string for Return is used there alone.
- **The icon button** (`IconButton`, 28 by 28) shows a glyph instead of a label. It has no constructor without a name, which is what VoiceOver reads, for example `tr!("a11y.copy_password")`, which the copy button of the secret field reads. An icon button can say whether it is on (`toggled`), as the button that reveals a secret does, and whether the menu it opens is open (`expanded`), as the footer's menu button does. Until the app's own glyphs arrive, the icon button takes a GPUI Kit icon.

### One copper surface per view

`Primary` and `Large` are the copper surface, and a view has at most one. In debug builds every copper button that is not disabled reports to a count per window while it renders. After the frame the count is kept, and a frame with more than one copper surface writes a line to stderr. `one_copper_per_view` draws a view with one primary button, a button of every other kind, a selected row with its ghost verb, the panel footer with its menu button and a secret field with its icon buttons, and holds the count to one; `the_copper_counter_sees_both_copper_kinds` checks that both copper kinds count and a disabled one does not.

## Keycaps and shortcut pairs

A keycap shows one keystroke as a Mac prints it: 18 high, at least 18 wide, radius 4, `Caption`. The modifiers come in the order ⌃⌥⇧⌘, then the key: Return as ⏎, Escape as "Esc", Tab, Delete, the arrows and Page Up and Down as their glyphs, a letter as its capital. GPUI's own text for a keystroke writes `^` for Control, puts ⌘ before ⇧ and spells out `enter`, so the glyphs are set in `keycap.rs`. Keys come in as GPUI key strings (`cmd-shift-c`), the same form the action registry keeps; a string GPUI cannot read fails in a debug build.

A keycap never stands alone. `Keycap` is visible inside `ui::ds` only, and a scan (`keycap_cannot_be_built_outside_ds`) keeps it from being named anywhere else in `src/`, `tests/` or `examples/`, in case the visibility is ever widened. Like the other scans over the source it reads the files through `code_only`, so a `//` inside a string such as `"https://"` cuts nothing off, and it leaves out comments and inline test modules. Inside the design system it is built in two places:

- A `Shortcut` pair: keycaps followed by the word for what they do, as in the panel footer ("⌘C Password"). Its constructor takes the word and panics on an empty one, in every build. The pair is not in the accessibility tree at all: it has no id and no role, and neither have its keycaps and its word, so GPUI writes no node for any of them. The keys reach VoiceOver only through `aria_keyshortcuts` on the control they act on, for which `keys_text()` gives the text, and the macOS adapter of AccessKit in `Cargo.lock` (0.26.3) does not pass that on. A hint row of shortcut pairs, such as the panel footer, has to put its text into the description of the focused element if VoiceOver users are to hear it.
- A `Button` with `.shortcut(keys)`: the keycaps follow the label, and the button's `aria_keyshortcuts` holds them. On a copper button, `Primary` or `Large`, a keycap has no surface of its own, only an edge in `keycap.on_accent.border`. A disabled button has no copper, so its keycaps keep their surface. `a_keycap_on_copper_has_no_surface_of_its_own` reads the quads painted in the place of the keycap on a button of each kind and on a disabled `Primary` and `Large`: no fill and that edge on the two copper kinds, `keycap.bg` with `keycap.border` on the others and on the disabled ones.

`keycap_never_alone` reads every file under `src/ui/ds` through `code_only` and finds `Keycap::new`, called or passed on as a function, in `shortcut.rs` and `button.rs` only, and in both.

`aria_keyshortcuts` gets the same glyphs as the keycap. Whether VoiceOver reads them in the user's language is unconfirmed until the adapter passes the value on and a device session hears it.

A pair for a command comes from `Shortcut::for_command(id)`, which reads the command table in `src/app/registry`: the first of the command's keys and its word, `(spec.label)()`, so a pair never names a command differently from the menus and keeps no word of its own. A command without keys, such as signing in to an SAP system, which Return reaches through the main action, shows its word alone, with no keycap. Closing the panel has two keys, ⌘W and Esc, and its pair shows ⌘W. `every_command_with_keys_makes_a_shortcut` walks the whole table.

## The text field

`TextField` keeps the GPUI Kit input, with its editing, selection, input methods and context menu, and changes four things about it:

- **Size.** Kit Medium is 26 high at text size 13 and writes 11.4 px. The field is 28 high and writes `Body`, at 13 as at 15, where it is 32.3 high. `Input::h` only sets the height of a multi-line input, so the wrapper sets it through the style, after the Kit's own. `text_field_writes_body_at_13_and_15` compares how wide the input lays out a value with the width of that value in `Body`, at both text sizes.
- **Name.** Without a name of its own, the Kit names a field after its placeholder, and macOS reads the placeholder as name and value at once. The field's label stands above it in `Callout` and is always its name.
- **Errors.** With an error the edge turns `field.border.error`, and a sentence with a glyph below says what is wrong. The Kit input takes no description, so the sentence is a node of its own (a label with the sentence as its value) that VoiceOver reaches right after the field.
- **Focus ring.** The Kit tints the edge of a focused input and lays a 3 px band at half opacity around it, without a gap (gpui-component 0.7.1, `src/styled.rs:11-12` and `:257-325`). The field turns that off with `focus_ring(false)` and shows the ring of every component around the input while the input's state has focus from the keyboard, so the edge keeps its color, carmine with an error too.

Password fields stay `SecretInput`.

## The switch

`Switch` keeps the GPUI Kit switch. The Kit paints a switch that is on in its primary color, which in this theme is copper; this one is `switch.on.bg`, the color of text, so copper stays with the one button that has it. The Kit writes its own label at 11.4 px; here the label stands beside the switch in `Body` and is the switch's name for VoiceOver, and a sentence below in `Callout` can say what changes. The Kit switch takes no description, so that sentence is a node of its own, a label with the sentence as its value, which VoiceOver reaches right after the switch, as with the error sentence of the text field. The track keeps the Kit's fixed 36 by 20 pixels at both text sizes. A disabled switch gets no handler.

The Kit's focus ring on the track is off (`focus_ring(false)`), and the track shows the ring of every component, a capsule around the 36 by 20 pixels. The Kit switch keeps its focus handle to itself, so the track sits in a wrapper that tracks a focus handle of its own, which is never a tab stop and writes no accessibility node. Focus inside the wrapper is the switch's: nothing else in there takes focus, and a press on the switch focuses the switch, not the wrapper. A disabled switch takes no focus, and its wrapper tracks none.

## The tile, the chip and the vault badge

These three are parts of a row. In a row they have no id and no role, so they write no node, and the row's name says in words what they show. On their own each one sits in a `Standalone`, a node with an element id, a role and a name, which panics on an empty name in every build: `Tile::standalone`, `Chip::standalone` and a badge's `standalone`. A row takes the plain types; how the tests keep a node of their own out of a row is described with the row.

- **Type tile.** The glyph of an entry's kind, 16 points, on a square of 28 points with a radius of 6 in `tile.bg`; on a selected row it takes `tile.selected.bg` and `tile.selected.glyph`. No letters from the title and no website icons. On its own, as in the head of an entry's details, it is an image named after the kind.
- **Chip.** 18 points high, radius 4, its text in `Caption`, with an optional glyph of 12 points, in one of six tones: neutral, production, attention, decision, danger and patina. A production system's chip is `prd.chip.bg` with `prd.chip.text`, ocher, never carmine, which is for what cannot be undone. The chip shows the text its caller gives it, a word from a text key or a fixed mark such as "PRD", and panics on an empty one. On its own it is a label named with its meaning spelled out, "Production system" for "PRD".
- **Vault badge.** The personal vault is a ring of 8 points, 1.5 px wide, in `vault.personal`. A team vault is a dot of 8 points in the team's color with its initial next to it, 3 points away, in `Caption` and `text.secondary`, so the color is never the only sign. Any other vault, a file whose audience FerrisPass does not know, is a dashed ring in `vault.other` with its initial. On its own the badge is an image named after the vault.
- **Initials.** `initial_for(name, others)` gives a vault its initial: the first letter of the first word that is not "Team", as a capital, so "Team Beratung" is B and "kunden-alt" is K. When the word of another vault starts with the same letter, the initials take a second letter as written in the word: in the order of the words, each takes the first letter after its first where its word differs from every word before it and that no word before it took. "Team Vertrieb" next to "Team Verwaltung" is Ve, and Verwaltung is Vw. Only letters and digits count, and two vaults with the same word keep the same initial.

No component sets a text size of its own. `nothing_below_11_points_in_the_new_components` reads every file under `src/ui/ds/components` through `code_only` and fails for a text size set any other way than through a text style: GPUI's `text_size` and its named sizes, and the GPUI Kit's sizes, which go down to 11.4 px at text size 13. No text style is below 11 points.

## The row and the result list

`Row` is one entry, the same in the quick panel, the command palette and the main window's list. It shows the type tile, the title with at most one chip, a second line and the vault badge, 44 or 28 points high in the main window's list and 44 or 32 in the panel (`RowDensity`). The two at 44 put the second line under the title: the customer, the client and the user between middle dots, cut off in the middle where they run out of room. The two smaller ones put the customer and the user on the title's line. In the panel a row also shows the keys that select it, ⌘1 to ⌘9, as a hint in `Caption` and `text.tertiary` after the badge, and puts them into its `aria_keyshortcuts`; the panel binds them. The hint is no keycap: a keycap stands next to the word for what its keys do, and here the row they select is that word. A ghost button with the row's verb shows while the row is selected or under the pointer.

- **States.** The title is in `RowTitle`, Medium, and on the selected row in `Headline`, Semibold, because the color of the selection is only about 1.2:1 against the surface. The selected row takes `row.selected.bg`, or `row.selected.unfocused.bg` while its list has no focus; its second line turns `text.primary` and its tile `tile.selected.bg`. While the keyboard is in use, the selected row of a list that has focus shows the focus ring inside its edge, where a list that scrolls cannot cut it off, and a click takes the ring away. A discreet row has no second line, so the customer and the user stay off the screen.
- **The pointer.** A row that is not selected takes `bg.hover` under the pointer and shows its verb. That is all it does: the row has no handler that selects, and it draws the selection it is given. `hover_changes_the_color_not_the_selection` moves the pointer over a row and away again, reads the surface the window paints in the row's place and the node of the row it drew, and checks that the row stays unselected and takes no color of the selection.
- **VoiceOver.** A row is one node, an option in a list box (`ListBoxOption`), with its place in the list counted from 1, the size of the list, whether it is selected, also while its list has no focus, and a description, which on the selected row is the panel footer's sentence. The tile, the title, the chip, the second line, the badge and the keys get no element id and no role, and the texts are plain strings, not text with an id, so they write no node; the next point says how far the tests read that. The verb is a button inside the option. The name comes from `RowParts::accessible_name`: the kind and the title, then the role, the customer, the client, the user and the vault, each after a comma, as in "SAP system NHP 100, Production system, Nordhafen AG, Client 100, N.WEISS, Team Beratung". A part that is missing or holds no word is left out, without a placeholder and without an empty comma. Each part is a word from a text key or a value of the entry, which the caller passes in. The row takes the role word as it is given and never makes one up from its chip, so "PRD" on the chip does not reach the name: `accessible_name_takes_the_role_word_as_given` draws a row with a "PRD" chip and the role word, one without a role word and one with a blank one, and each reads the name its parts give, with "PRD" nowhere in its node. That the caller passes "Production system" and not the letters needs a test where the panel builds its rows, which comes with the panel. Any other element that stands for an entry can take the same name from the same function.
- **One node.** The row builds what it draws inside its node in one place, `Row::inside`: the tile, the title, the chip, the second line, the badge, the keys and the verb. Its render keeps the row's own node and lines the parts up with `lay_out`. In `Row::inside` the title, the second line and the keys are plain boxes, and GPUI gives a role only to an element with an id, so a role on one of those boxes, and with it a node, does not compile. Two things do compile: an element id set through the box's `interactivity()`, which the first of the tests below finds, and a text with an id inside one of the boxes, which GPUI writes as a label and the second finds in the source. `the_tile_the_chip_and_the_badge_write_no_node_in_a_row` renders each part `Row::inside` builds, selected and not and with each kind of badge, and finds neither a role nor an element id on the element each of them renders to: the tile, the title, the chip, the second line, the badge or the keys. That leaves out the boxes `lay_out` puts around the parts and the text inside the title, the second line and the keys, so `a_row_gives_an_id_and_a_role_to_its_own_node_only` reads `row.rs` through `code_only`. It finds one call that gives an element an id and one that gives it a role, written as a method (`.id(`) or through its trait (`InteractiveElement::id(`), and `a_row_is_a_list_box_option_with_its_place_in_the_set` finds both on the row's own node. It finds none of the calls that build a text with an id (`Text::new`, `text!`, `with_id`, `InteractiveText`) and no `standalone` or `Standalone`: no part is shown on its own inside the row. What the tile, the chip and the badge draw inside the element they render to, the glyph, the chip's text and the badge's initial, is not read by rendering either, since GPUI keeps an element's children to itself. `the_tile_the_chip_and_the_badge_give_no_node_to_what_they_draw` reads `tile.rs`, `chip.rs` and `vault_badge.rs` through `code_only` and finds no call that gives an element an id or a role, written as a method (`.id(`) or through its trait (`InteractiveElement::id(`), none of the calls that build a text with an id (`Text::new`, `text!`, `with_id`, `InteractiveText`), which GPUI writes as a label, and one `Standalone` in each file, built in the constructor of the part on its own and called nowhere in the file. What the two scans cannot see is under "Limits".
- **Accessibility id.** A row takes the caller's `AccessibilityId` and applies it like every other component, so an entry's title cannot reach it.

The result list is not built yet. The plan was a `uniform_list` with the role `ListBox` and its name, with the selected row as the active descendant while focus stays in the search field. Two things in GPUI (`gpui-pre` 0.3.8) stand against that: `uniform_list` writes no node of its own, so the role and the name of the list get lost, and GPUI reports an element as the focused one in the tree (`aria_active_descendant`) only while an ancestor of that element has focus, while the panel's search field is the GPUI Kit's text input next to the list, not around it. So the row does not report itself as the focused element yet. How the list lets VoiceOver hear the selected row is decided with the list, which comes next on this branch, and so does moving the selection with the arrow keys and ⌘1 to ⌘9.

## The secret field

`SecretField` shows a password, or another secret of an entry, as the panel and an entry's details show it. The caller hands it the secret as a `Zeroizing<String>` and says whether it is revealed, whether assistive technology is running and what a copy shows. The field finds out none of that itself and keeps no timer.

- **Hidden** it shows twelve dots in `Secret`, whatever the length of the secret, so the length cannot be read off the screen. A field without a secret shows the same dots. `a_hidden_secret_shows_twelve_dots_whatever_its_length` draws a secret of 4 characters and one of 40 and finds the value equally wide; revealed, the one of 40 is wider, so the width follows what is drawn.
- **Revealed** it shows the secret in `Secret`, in groups of four, its letters in `text.primary`, its digits in `secret.digit` and every other character in `secret.symbol`. The text is GPUI's styled text without an id, which writes no node. When revealing ends is the caller's to say: on a new selection, when focus leaves, when the app locks and after 60 seconds, the panel sets `revealed` back.
- **Copying.** The value is a button that copies, and a copy button stands at the end of the field. Both run the handler the caller gives to `on_copy`, which hands the secret to the clipboard service; the field never copies. Without that handler there is no copy button, and the value is a plain box without an id or a role. Right after a copy the caller sets `CopyState::Flash`, which paints the value in `bg.selected` and puts a tick on the copy button, then `Check`, which keeps the tick, then `Idle`.
- **Revealing.** The button that reveals and hides the secret runs the handler given to `on_toggle_reveal`; without one the field has no such button.
- **VoiceOver.** The field is a group named with its label, such as "Password". The value is a button named "Copy password" (`a11y.copy_password`), described as "hidden" (`a11y.hidden`) while the secret is, whose node offers VoiceOver's press. The button that reveals is an icon button named "Show password" (`a11y.reveal_password`) that says whether it is on, and the copy button an icon button named "Copy password". A field without a copy handler says "hidden" on its group instead. The secret is in the tree only as the value of the value button, and only while it is revealed and the caller says assistive technology is running (`assistive(true)`). The value is the field's first tab stop, before the two buttons; it copies on Return and Space and shows the ring of every component for focus from the keyboard (`the_value_copies_from_the_keyboard_and_shows_the_focus_ring`).
- **Accessibility id.** The field puts the caller's `AccessibilityId` on its group, like every other component.

No code read `a11y.copy_password` and `a11y.reveal_password` before the field; it does now, so their lines in `locales/_reserved.txt` are gone.

## The one-time code ring

`OtpRing` shows how long a one-time code still holds. A canvas draws the ring with `PathBuilder::arc_to`, 16 points across in a row and 18 in an entry's details: the track in `otp.track`, a full circle, and over it, clockwise from the top, the share of the period that is left, in `otp.ring`, or in `otp.ring.warn` below five seconds. Both are strokes of 2 px. Before the ring stand the code in `Code`, in groups of three ("739 114"), and the seconds left, rounded up, in `Callout` with digits of equal width ("18 s"). The ring keeps no timer: the caller draws it again, ten times a second, with the time left.

- **Masked** is the default, as in the panel: the code shows as "••• •••", whatever it is.
- **The next code.** Unmasked, the next code stands beside the current one in its last five seconds, in `text.tertiary`. A masked ring does not show it.
- **VoiceOver.** The ring is a timer named "One-time code, expires in 20 seconds" (`a11y.one_time_code_expires`). The seconds are rounded up to a multiple of five (`announced_seconds`: 18 is 20, 13 is 15, 4 is 5, 0 is 0), so the name changes at most every five seconds. The code is in the tree only as the timer's value, "739 114", while the ring is unmasked and the caller says assistive technology is running. The next code never is.

## Secrets in the tree

The secret field and the ring are built from several elements, and the test platform builds no accessibility tree, so a test that read the node of the outer element would show nothing about the others. Each of the two makes its elements in `build`, puts them into one another in `assemble`, and, under `cfg(test)`, lists them with `parts()`: the group, the value, the dots or the revealed text, the focus ring while it shows and the two icon buttons of the field; the timer, the boxes of the code, the next code and the seconds with the text each holds, and the ring of the ring. `parts()` reads the node of each element before it goes into its container, since GPUI reports no node for an element whose type it has erased. The outer element, the group and the timer, it reads off the element `render` returns, so whatever is set on it on the way is read too. `parts()` names every field of what `build` returns, so an element added there does not compile until it is listed.

- `no_secret_in_ax_tree` puts the secret "sp-test-7Qx!2026" into the field and the code "739 114" with the next code "205 881" into the ring, and reads the label, value, description, tooltip, author id and placeholder of every part. Hidden without and with assistive technology and revealed without it, in each copy state and with and without the handlers, no part holds the secret, all of it or a group of three or four of it, alone or in a row. Revealed with assistive technology, the value of the value button holds it and nothing else does. The same goes for the ring, masked without and with assistive technology, unmasked without it, with and without the next code: only the timer's value holds the code, unmasked with assistive technology, and nothing ever holds the next code.
- `every_rendered_child_is_a_part` holds each component to its list. The containers the two files build note under `cfg(test)` how many children they hold once they are laid out. The test draws the field hidden and revealed, without and with assistive technology, in every copy state, without and with its handlers and without and with a secret, and the ring masked and unmasked, without and with assistive technology, with 18 and with 3 seconds left and without and with a code. In each it finds as many elements drawn, the one returned and the children of the containers, as parts listed, so a child put into one of the containers that is not on the list makes the counts differ, also one that only one state adds, such as a child only while assistive technology runs or only while a copy flashes. An element put around a part takes the part's place in its container and leaves the counts as they were; the next test keeps `assemble` from doing that.
- `assemble_only_places_parts` reads `assemble` in `secret_field.rs`, `otp.rs` and `panel_footer.rs` through `code_only` and holds it to putting parts in place. Its body may call `child`, `children`, `map`, `into_iter` and `into_any_element` on an element, read a field of `Built`, call the variants it matches and a closure of its own, and name what it binds. Any other word fails, and so does a macro, a literal or an attribute, so a `div()` around a part, an id, a role or a name set on one, or a keycap shows up with the words it takes.
- `secret_text_has_no_role` reads `secret_field.rs` and `otp.rs` through `code_only` and finds none of `text!`, `Text::new`, `with_id`, `InteractiveText` and the GPUI Kit's `Label::new`, which give a text an id or a node of its own. `Text::new_inaccessible` is allowed.
- `neither_secret_component_can_be_printed` holds the field and the ring to having neither `Debug` nor `Display`, read at compile time, since `Debug` of a `Zeroizing<String>` writes the secret, and finds no macro in either file that prints, writes or logs.
- `the_secret_field_never_touches_the_clipboard` reads both files for the clipboard, the pasteboard, `write_text` and `write_secret`, in any spelling.
- `the_secret_components_show_no_tooltip` reads both files for a tooltip. GPUI's tooltip is a view of its own that opens under the pointer, not a property of the node `no_secret_in_ax_tree` reads, so a tooltip could show the secret past the dots and past that test.

## The panel footer

`PanelFooter` is the footer of the quick panel. Its first line, in `Headline`, says what Return does for the selected entry, with its target and its user ("⏎ Sign in to NHP, client 100 as N.WEISS"); its second, in `Callout`, holds up to three more shortcut pairs and, for some tones, a short note; a third can say what to connect to first, with a glyph. The button at its end, an icon button named "More actions" (`a11y.more_actions`), opens the menu with locking, opening FerrisPass and the settings, runs the handler the footer is built with, and says whether the menu is open (`aria_expanded`). The lines are shortcut pairs, from `Shortcut::for_command` or `Shortcut::from_keystroke`; a pair without keys shows its words alone, as the line that tells to choose a production system first does.

- **Tones.** `FooterTone` colors the first line: ochre (`status.attention.text`) with a glyph while Return waits for a production system to be chosen, blue (`status.decision.text`) while a decision is open, and ochre once the caller says the decision is stale, a day after it came up. Offline, matches that look the same and a waiting update each add a note at the end of the second line, in ochre, in `text.secondary` and in `text.tertiary`.
- **At most three more pairs.** A fourth fails in a debug build and is left out in a release build. `the_footer_shows_at_most_three_more_shortcuts` runs `more` a fourth time with the debug check off for its thread, as a release build does, and finds three pairs drawn and three in the description.
- **No focus and no node.** The footer has no element id and no role, and only its menu button takes focus: `the_footer_is_not_focusable_and_writes_no_live_node` reads every element the footer builds, the footer itself off the element `render` returns, in every tone, and finds an id and a role on the menu button only, no role that announces itself (alert, status, log, marquee, timer) and no live region, and in a window that holds the footer alone Tab finds one stop, the button. Like the field and the ring, the footer makes its elements in `build` and puts them in place in `assemble`, which `assemble_only_places_parts` holds to that.
- **Its text for VoiceOver.** `description_text()` gives everything the footer shows as sentences, each pair with its keys: "⏎ Sign in to NHP, client 100 as N.WEISS. ⌘C Password, ⇧⏎ Type into SAP GUI, → More. As of 13:40. Connect first: Nordhafen GP (VPN)". The panel puts it into the description of the search field and of the selected row; the row takes it through `Row::description`.

## Deviations

- **The switch's thumb moves with the Kit's spring** also when the switch is toggled from the keyboard. Keyboard actions without animation need to know which kind of input caused them, which comes with the motion module later.
- **GPUI Kit icons.** Until the app's own glyphs arrive, the type tile, the chip's glyph, the icon button, the buttons of the secret field and the glyphs of the footer take GPUI Kit icons.
- **No times for the flash and the tick.** A copy flashes the value and puts a tick on the copy button for as long as the caller says, through `CopyState`; the 120 ms of the flash and the 1.2 s of the tick come with the motion module.
- **Whether assistive technology is running is a parameter.** The secret field and the ring take it from the caller through `assistive(bool)` and never find it out themselves; the panel sets it from macOS.
- **The tests read nodes, not elements.** `parts()` returns what each element tells assistive technology, read before it goes into its container, rather than the elements: GPUI reports no node for an element whose type it has erased, so a list of erased elements would read empty. The outer element is read off what `render` returns, which still has its type.
- **The update note carries its words.** `FooterTone::UpdateReady` takes its note like `Offline` and `Tie` do, since the footer has no text of its own.
- **The seconds next to the ring carry the symbol `s`**, written in the code. It reads the same in English and German, and there is no text key for it.
- **No result list yet, and no active descendant.** The selected row does not report itself as the focused element of the tree, and the result list is not built; see "The row and the result list".

## Limits

- The copper count sees what renders. A view drawn from GPUI's view cache does not render again and does not report, and a frame without copper leaves the count of the last frame that had some. Nothing in the app uses the view cache.
- The macOS adapter of AccessKit (0.26.3) does not pass `aria_keyshortcuts` on to VoiceOver yet. The buttons set it anyway, so it arrives with the adapter; whether VoiceOver then reads the glyphs in the user's language is unconfirmed until a device session hears it. A shortcut pair writes no node at all, so a hint row is silent for VoiceOver until its text goes into the description of the focused element.
- The same adapter hands `DefaultButton` to VoiceOver as a plain button (`accesskit_macos-0.26.3/src/node.rs:72`), so VoiceOver reads the default button like any other button today, by its name and description, and hears no ⏎. `default_button()` does not bind Return; the screen binds it, as it binds the keys of `shortcut()`.
- GPUI has no disabled flag for assistive technology. A disabled button says "not available" in its description; the Kit text field and switch take no description, so a disabled field or switch is only greyed out and does nothing.
- The Kit switch and input take an accessibility id only where the Kit offers one: the text field passes it on, the switch has none.
- The keycap scan, like the other scans over the source, leaves out inline test modules; a keycap built in a test outside `src/ui/ds` is past it, and the visibility of `Keycap` still keeps it from compiling.
- The literal scans see a literal handed straight to a call, in the place of its text. One that reaches a call through a variable or inside another call, such as `SharedString::new_static("..")`, is past them, and so is a constructor called as `Self::new` or through a renamed import; for the button's own descriptions `no_unused_keys` notices, because nothing else reads their keys.
- Only code in `accessibility_id.rs` can build an `AccessibilityId` as a tuple, only code in `ui::ds` can call `new`, and the source check reads text, not types. A second constructor added in `accessibility_id.rs`, a call to `new` written another way (through a renamed import or a type alias, `Self::new`, spaces in the path, or a macro), and a file outside `src/ui/ds` that becomes part of `ui::ds` through `#[path]` or `include!` are past both. Inside an inline test module a call may pass anything; that code is built for the tests only.
- `the_default_role_is_set_behind_its_guard_only` reads text, not types. Inside the module `default_role`, a flag built or written through a macro is past it. Outside the module the compiler keeps code from building the flag or naming the ⏎ key string, but not from copying both from a button that passed the check, or from changing the kind of a danger button around a call to `make_default`. `a_danger_button_never_becomes_the_default_button` catches such code in the constructors, in `default_button`, in `make_default` and where the button is drawn; in a builder method the test does not call, such as `shortcut()` or `disabled()`, it is past every test.
- Once the spinner shows, the Kit spinner's own animation asks for frames, so the frame test cannot tell whether the button stops asking after the delay.
- The test platform paints no glyphs, so the error sentence test knows a painted line by its place, its color and its width, not by its letters. Another text exactly as wide as the sentence would pass it; the accessibility node of the error line holds the sentence itself.
- The test platform builds no accessibility tree and cannot deliver VoiceOver's press, so the tests read each element's node, check in the source that the press is registered next to the click, and call the press directly. That VoiceOver reaches the switch's sentence right after the switch, as it does the text field's error sentence, follows from the order of the nodes and is not read back in a test. The source check reads the code, not what GPUI does with it: that the press arrives on a real Mac, and how every component looks against the component board, need the gallery and a device session. They come later.
- A chip on its own is a node with the role `Label`, which the macOS adapter of AccessKit hands to VoiceOver as static text, with the name as its title (`accesskit_macos-0.26.3/src/node.rs:44`, `:306`). Whether VoiceOver reads that title for a chip on its own is for a device session.
- The variants of `VaultBadge` are public, so a badge written as `VaultBadge::Team { .. }` skips the check for an empty initial in `VaultBadge::team`, and the literal scan reads the constructors only.
- `no_uppercase_in_new_modules` looks for the call that sets a whole text in capitals. `initial_for` makes its one capital with `char::to_uppercase(first)`, which that scan does not see, and neither would it see a whole text mapped through it.
- The text size scan reads the components' own calls. The GPUI Kit controls inside the text field and the switch set their own sizes, as described above.
- The row takes the role word as the caller gives it. That a caller passes "Production system" and never the letters "PRD" needs a test where the panel builds its rows, which comes with the panel; here only that the row adds nothing of its own to its name, the letters on its chip included, with a role word, without one and with a blank one.
- `a_row_gives_an_id_and_a_role_to_its_own_node_only` reads the text of `row.rs`, not types and not the tree GPUI builds. A node inside the row made without one of its calls written out in `row.rs` is past it: a macro defined in another file that expands to one of them, `Text`, `InteractiveText` or the `text!` macro imported under another name, a helper function in another file that returns an element with an id and a role or a text with an id, an element type of its own that reports a role through `a11y_role`, or another component or GPUI Kit control that brings a node of its own. `the_tile_the_chip_and_the_badge_write_no_node_in_a_row` reads the element each part renders to, not what is inside it or the boxes around it. `the_tile_the_chip_and_the_badge_give_no_node_to_what_they_draw` reads text too: a node inside the tile, the chip or the badge made another way, through a macro other than `text!`, a renamed import, a function outside the part's file, or another element, component or GPUI Kit control that brings a node of its own, is past it. The test platform builds no accessibility tree, so only a device session with VoiceOver shows the real tree of a row.
- The separators in a row's name and on its second line, a comma and a middle dot, are punctuation in the code, the same in English and German; the literal scans see no word there.
- `raw_accessibility_ids_are_applied_in_one_file` reads text, not types, and only under `src/ui/ds`. A method name that a macro puts together is past it, and inside an inline test module a call may pass anything. The screens under `src/ui/windows` get the same check when the first of them uses the components.
- A row learns that the pointer is over it from the pointer's moves. A window drawn under a pointer that has not moved yet paints the hover color, which GPUI takes from where the pointer is, but shows the verb only after the first move.
- With increased contrast a selected row is meant to get an inner border in `row.selected.border`. The row does not draw it yet.
- What VoiceOver hears for the secret field, the ring and the footer needs the panel and a device session too: whether it reads "hidden" after the name of the value button, the timer's name every five seconds, and the footer's text in the description of the element that has focus. The tests read each element's node.
- The secret reaches the tree only as the value of the value button. A field without a copy handler has no value button, so VoiceOver does not hear a revealed secret there, even with assistive technology running. The panel always gives the handler.
- The value of the secret field registers VoiceOver's press next to its click handler, as the button does, so the press calls the handler instead of clicking the middle of the value. No test reads that registration for the value, as `button_click_reaches_voiceover` does for the button, and the test platform cannot deliver a press.
- The copy and reveal buttons are named for a password. A secret of another kind needs names of its own, which come with the screens that show one.
- Drawing a revealed secret or a code, and putting either into the tree as a value, hands GPUI a copy of the text, which GPUI keeps in its text layout and its accessibility data and does not wipe. The field and the ring wipe only their own copies: the `Zeroizing<String>` they hold and the grouped text they build.
- `parts()` lists the elements `render` builds, not the nodes of a real tree, and `every_rendered_child_is_a_part` counts the children of the containers the two files build, in the states it draws. What the icon buttons and the canvas draw inside themselves is the button's and GPUI's: a child put into one of them, or a node GPUI adds on its own, is past the count. The focus ring of the value shows only while the value has focus from the keyboard, which the count does not give it, and notes no children, so a child put into the ring in `build` is past the count too.
- `assemble_only_places_parts` reads text, not types. A function of the same file called from `assemble` under one of the names it may use is past it, and so is an element made in `build` around a part when `parts()` binds its field to `_`.
- `no_secret_in_ax_tree` looks for the secret, all of it and its groups of three and four, and for nothing shorter. A part that holds two characters of it, or the secret in another form, reversed or encoded, is past it.
- `secret_text_has_no_role`, the macro part of `neither_secret_component_can_be_printed`, `the_secret_field_never_touches_the_clipboard` and `the_secret_components_show_no_tooltip` read text, not types: such a call written through a renamed import, a macro or a function in another file is past them. The `Debug` and `Display` part of `neither_secret_component_can_be_printed` reads the types and sees an implementation wherever it is written.
- The test platform keeps the paths of a frame to itself, so `the_ring_warns_below_five_seconds` reads the paths `ring_paths` builds for the canvas: their colors, that every point of them lies on the ring, and that the time left covers its share of the turn from the top. That the canvas paints exactly these is read in the code, not in the frame.
- The footer is no node. Its text reaches VoiceOver only if the panel puts `description_text()` into the description of the element that has focus, which a test of the panel shows when the panel is built.
- The literal scan reads the footer's notes where they are written as `FooterTone::Offline(..)` and so on. After a `use FooterTone::*`, a note written as `Offline(..)` is past it, like any constructor called through a renamed import.
- What VoiceOver says for a row, and whether it reads the selected row's description, needs the panel and a device session. The keys that select a row reach VoiceOver only through `aria_keyshortcuts`, which the macOS adapter does not pass on yet (see above).
