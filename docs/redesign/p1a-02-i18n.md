## How keys are named

A key is a path of English segments in snake_case, from the area to the element: `quick.footer.prd_select_first`, `msg.offline`, `glossary.vault.team`.

| Prefix | For |
|---|---|
| `common.*` | Everyday buttons many screens share: Cancel, Later, Back, Done, Why? |
| `glossary.*` | The names of entry kinds, vault kinds and a few other things that appear everywhere |
| `msg.*` | The standard messages, one key per situation. A screen that meets the situation uses the key instead of writing its own sentence |
| `quick.*`, `menubar.*`, ... | One prefix per screen or surface |
| `a11y.*` | Accessible names for controls without visible text, such as icon buttons |
| `bundle.*` | Texts macOS shows from the app bundle, such as the Touch ID prompt |
| `action.<id>.label`, `.help` | Reserved for the action registry. A screen never names a registry action with its own words |
| `*.tech.*` | Technical details, which keep the words of the trade |

- A key with the segment `playful`, such as `empty.vault_new.playful`, holds a playful line. It never sits under a key that has to stay factual (security, errors, sync, typing); `design/glossary.toml` lists those.
- A plural key has two forms, `key.one` and `key.other`, and `tp!` picks one for the count. English and German share the rule: one for 1, other for everything else. No other key ends in `one` or `other` (`glossary.vault.other_vault`, not `glossary.vault.other`).
- Placeholders have names: `%{vault}`, `%{time}`. Sentences are never put together from pieces. Counts get their thousands separator from `tp!`; dates and times come from `i18n::fmt`, which asks macOS.

## Where things live

| Path | What |
|---|---|
| `locales/<prefix>.yml` | The catalogues, `_version: 2`, English and German next to each other |
| `locales/kit.yml` | German for the GPUI Kit texts the app shows (text field context menu, dialog buttons, empty lists). The Kit ships no German; `i18n::init()` hands this namespace to the Kit with `rust_i18n::extend!` |
| `locales/_reserved.txt` | Keys no code reads yet, each with what will read it |
| `design/glossary.toml` | Words to use and words to avoid in both languages, phrase rules, words allowed only in SAP texts, and the style rules |
| `src/i18n/mod.rs` | `tr!`, `tp!`, `ui_language()`, `init()`, `GERMAN_ENABLED`, and `CATALOGUES` |
| `src/i18n/fmt.rs` | Numbers, dates and times |
| `src/i18n/tests.rs` | The tests below |
| `bundle/macos/en.lproj/InfoPlist.strings` | The English Touch ID prompt text; `scripts/build-mac.sh` copies every `.lproj` folder into the bundle |

rust-i18n reads `locales/` while it compiles the crate but does not tell Cargo, so an edited catalogue alone would not trigger a rebuild. `CATALOGUES` in `src/i18n/mod.rs` includes every file with `include_str!`, which does. A new catalogue goes into that list; a test fails until it does.

The command line tool never uses text keys and never calls `i18n::init()`. Its output is an interface for scripts and stays English.

## What the tests check

rust-i18n only notices a missing key at runtime, and then shows the key itself, or the English where the German is missing. These tests close that gap. They read the compiled catalogues, `design/glossary.toml` and the source under `src/`.

| Test | Fails when |
|---|---|
| `every_key_has_both_languages` | a key lacks English or German, a text is empty, or a plural key has only one form |
| `placeholders_match` | the two languages use different placeholders, or a placeholder is not a snake_case name |
| `used_keys_exist` | a `tr!` or `tp!` in `src/` names a key (or plural form) that does not exist, passes a value the text does not use or misses one it needs, or takes its key from anything but a literal; also when code reads texts in a way the scan cannot see (`i18n::text`, rust-i18n's `t!`) |
| `no_unused_keys` | a key is neither read by code nor listed in `locales/_reserved.txt`, or a reserved key no longer exists or is read by code by now |
| `glossary_lint` | a text uses an avoided word, an opened vault, "Mandant" or "client" outside SAP texts, a long dash, "!" in a security or error text, "Fehler:" or "Error:" at the start of a sentence, capitals outside the list, or the polite German "Sie" and "Ihr" |
| `msg_unique` | a standard message is missing, a `msg.*` key is not a standard message, or two texts start with the same four words |
| `playful_only_where_allowed` | a `playful` key sits under a key that stays factual |
| `no_literals_in_render_code` | a string literal goes straight into `.child(..)` or `aria_label(..)` in `src/ui/ds` or `src/ui/windows`, keycaps and identifiers such as PRD aside. Those folders have no texts yet, so the test has nothing to find today |
| `cli_never_uses_text_keys` | the command line tool uses a text key or reaches into `i18n` |
| `only_the_app_starts_i18n` | `i18n::init()` is called from anywhere but `app::run`, or `extend!` appears a second time |
| `extend_adds_german_to_kit_strings`, `kit_texts_keep_the_kit_english` | a Kit text the app shows has no German, or the app changes the Kit's English |
| `german_bundle_texts_wait_for_german`, `the_bundle_texts_come_from_the_catalogue` | see below |

The glossary and style rules are checked in both languages; `the_glossary_rules_fire_in_both_languages` shows each rule catching a German and an English example.

## Why German is still off

The old main window still has its English texts written into the code. Switching German on now would put German next to English in the same app, so `GERMAN_ENABLED` in `src/i18n/mod.rs` is `false` and the app shows English even on a German Mac. Every key has its German already, and the tests keep it that way.

The bundle follows the same rule. As soon as a `de.lproj` folder is in the app bundle, macOS treats the app as German-speaking and shows its own texts for the app in German, the Touch ID prompt among them. So the bundle ships only `en.lproj` for now, and the German Touch ID text waits in `locales/bundle.yml`. German comes on in one step:

1. `GERMAN_ENABLED = true`.
2. `bundle/macos/de.lproj/InfoPlist.strings` with the German from `locales/bundle.yml`.
3. `CFBundleLocalizations` with `en` and `de` in `Info.plist`, so macOS offers FerrisPass in the per-app language setting.

`german_bundle_texts_wait_for_german` fails if one of the three moves without the others, and `the_bundle_texts_come_from_the_catalogue` checks that every `InfoPlist.strings` and `Info.plist` itself say what the catalogue says.

## Checks

All five gates pass on every commit: `cargo fmt --all --check`, `cargo clippy --locked --all-targets --all-features -- -D warnings`, `cargo test --locked`, `cargo audit`, and the dash scans over tracked files and the commit messages.

`Cargo.lock` gains dependency edges only: `rust-i18n` for the app, `regex` and `toml` for the tests. All three were in the lock already (rust-i18n 4.2.1 through GPUI Kit), so no package and no version changes.

`scripts/build-mac.sh --skip-notarize` builds, signs and seals the app with `Contents/Resources/en.lproj/InfoPlist.strings` inside and `CFBundleDevelopmentRegion` `en` in its `Info.plist`. On a Mac set to German, `NSBundle` resolves the built app to English (`localizations` and `preferredLocalizations` are both `["en"]`).

Each test was checked against a deliberate break: a `tr!` in `src/cli.rs`, a missing German text, German chosen without the switch, `init()` without its `Once`, a key that does not exist, "Datenbank" in a German message, "!" in an English one, "Sie" mid-sentence, an opened vault, a renamed standard message, a key missing from `_reserved.txt`, a literal in `src/ui/ds`, a `de.lproj` folder, and a changed `InfoPlist.strings`. Every break turned the matching test red. The PR lists each with its failing output.

A review of the change asked two questions: can a missing key show up as its name or as empty text without a failing test, and can German, a second `extend!` or a text key reach the app or the command line tool while German is off. The second found nothing. The first found that the source scan only recognized `tr!` and `i18n::text(` written without spaces, so `tr !("missing.key")` or a renamed import would have slipped past it; the last commit before this page fixes that, with a test for each way around it.
