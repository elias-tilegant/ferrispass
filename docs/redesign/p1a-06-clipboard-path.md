# P1a.06: One clipboard path

Every secret FerrisPass copies now goes through one clipboard service in `src/app/services/clipboard.rs`. It lives in a GPUI global instead of the main window, so the menu bar panel and the sign-in helper that come later can copy without a window and get the same clearing. The only change a user can see: a password FerrisPass put on the clipboard no longer survives quitting, and, with the right system setting, no longer survives a crash and a relaunch either.

## The one path

`ClipboardService::write_secret` is the only way a secret reaches the clipboard. The main window's `copy_with_auto_clear` is now a wrapper: it calls the service and shows the toast. It no longer has a timer, a countdown task or a write token of its own; the countdown pill reads the service's deadline and re-renders when the service notifies.

If the secret-aware write fails, nothing is written, an earlier copy of ours is cleared, and the caller gets the error. There is no fallback to a plain clipboard item that a history tool or Universal Clipboard would keep. That was already true in the main window and is now a rule of the service.

Every copy FerrisPass makes for you, from a button, a shortcut or a menu, takes this path: passwords, usernames, URLs, TOTP codes and custom fields. Copying by hand out of the entry editor does not. The password, the TOTP secret and custom fields marked protected can't be copied out of the editor at all; that block lives in `SecretInput` and stays. Text selected in one of the editor's unprotected fields (title, username, URL, notes, custom fields not marked protected) and copied with Cmd+C, Cmd+X or the context menu goes to the clipboard as a plain item, as it did before this change: no privacy types, no marker, no clearing. Whether the clipboard rule in SECURITY.md has to cover those copies is not settled yet; see Limits.

The "Copy code" button in the sign-in flow also writes to the clipboard directly. It copies the one-time code Microsoft shows for device sign-in, which the user types into Microsoft's page and which is not a credential.

## What the markers mean

Each item FerrisPass writes carries five types:

| Type | Meaning |
|---|---|
| `public.utf8-plain-text` | the secret itself |
| `org.nspasteboard.ConcealedType` | a password or similar; history tools should not show or keep it |
| `org.nspasteboard.TransientType` | short-lived; history tools should not record it at all |
| `org.nspasteboard.AutoGeneratedType` | not typed by the user |
| `rs.ferrispass.clipboard.secret` | written by FerrisPass; how a later launch recognises our copy |

The three `org.nspasteboard` types are a convention that clipboard managers honour, not something macOS enforces. The item is also written with `CurrentHostOnly`, which keeps it out of Universal Clipboard. That one macOS does enforce.

## What is cleared when

Clearing always compares the pasteboard generation first: if anything was copied after our copy, the clipboard is left alone. The service keeps that generation, never the secret.

Each test below was checked by breaking the rule it names, and it failed every time. The changed lines and the failing output are in [PR #16](https://github.com/elias-tilegant/ferrispass/pull/16).

| When | What happens | Held by |
|---|---|---|
| The timer runs out | cleared; a newer copy replaces the timer, and a timer for a replaced copy does nothing | `timer_clears_only_its_own_write` |
| "Never" is set | no timer, but the copy stays ours and is cleared at lock and quit | `never_setting_keeps_ownership_for_lock` |
| Something else was copied after ours | nothing is cleared, by the timer or by anything else | `clear_leaves_newer_clipboard_alone`, `delayed_clear_does_not_erase_newer_clipboard_contents` |
| A write fails | the earlier copy is cleared, the caller is told | `write_failure_fails_closed` |
| Lock, from the button, Cmd+L, closing the window, the idle or screen lock, switching vaults | cleared | `lock_clears_clipboard_ownership` |
| Quit with Cmd+Q or the menu, or restart into an update | cleared before macOS is asked to quit | `quit_clears_only_unchanged_own_copy` |
| Any other quit | cleared in the app's quit handler | `quit_clears_only_unchanged_own_copy` |
| Launch, with "Paste from Other Apps" set to Always Allow | a copy with our marker is cleared, if nothing was copied during the check | `start_clears_only_own_marked_copy` |
| Launch, with any other setting | nothing; the clipboard is not looked at | `start_clears_only_own_marked_copy`, `access_behavior_maps_every_appkit_value` |

## Why the launch check never reads contents

Since macOS 15.4 an app that reads what another app put on the clipboard can trigger a prompt asking the user to allow it. A password manager that shows that prompt at every launch teaches people to click it away, and the launch check has no reason to see the contents anyway: it only needs to know whether the item on the clipboard is ours. Asking for one type with `availableTypeFromArray` answers that. Reading the generation and the access setting doesn't show anything either.

Three things hold this:

- `Pasteboard`, the surface the service works through, has no method that returns contents.
- The test pasteboard counts reads through a method the trait doesn't have, and `start_path_never_reads_content` runs the launch check for every access setting, with our copy and with someone else's, and expects the count to stay at zero.
- `clipboard_code_never_reads_pasteboard_content` in `tests/architecture.rs` scans the clipboard code and fails on `stringForType`, `dataForType`, `propertyListForType`, `pasteboardItems` or `readObjectsForClasses` outside `#[cfg(test)]`.

## The access setting

`NSPasteboard.accessBehavior` tells an app what the user chose under Privacy & Security, "Paste from Other Apps". The launch check reads it first and goes on only for Always Allow. With Default (FerrisPass never triggered the prompt), Ask or Always Deny it stops there: no types, no generation, no clear. With Always Allow it takes the generation, checks for our marker type, and clears only if the generation hasn't moved since. The decision is `start_action`, a plain function of the setting and a closure for the marker check, so the closure is only called for Always Allow.

`access_behavior_from` in `src/clipboard_macos.rs` turns AppKit's raw value into ours. `access_behavior_maps_every_appkit_value` runs it over the four values Apple defines (0 Default, 1 Ask, 2 Always Allow, 3 Always Deny) and over values it doesn't. Only 2 comes out as Always Allow; anything unknown reads as Default, so a value a later macOS adds keeps the check closed.

On a Mac where `accessBehavior` doesn't exist (before macOS 15.4) the check reports Default and does nothing. FerrisPass requires macOS 26, so this only matters for tests on older machines.

## How to check by hand

On a preview build, with the clear delay at its default of 10 seconds. `pbpaste` in Terminal shows what is on the clipboard.

- Copy a password and wait 10 seconds: `pbpaste` prints nothing. Holds under every "Paste from Other Apps" setting.
- Copy a password and quit with Cmd+Q before the 10 seconds are up: `pbpaste` prints nothing. Holds under every setting.
- Copy a password, end FerrisPass with `kill -9` and start it again: with Always Allow, `pbpaste` prints nothing once FerrisPass is up. With Default, Ask or Always Deny it still prints the password. That is the gap described under Limits, not a failure.
- Copy a word in TextEdit and start FerrisPass: `pbpaste` still prints the word. Holds under every setting.

None of these should bring up a paste prompt for FerrisPass. Under Ask that is untested (SP13 in `docs/gpui-matrix.md` could not set it), so a prompt there is worth writing down.

System Settings lists an app under "Paste from Other Apps" only after it has asked for access (also SP13), so FerrisPass may not show up there. In that case the third check shows which value FerrisPass reads: `pbpaste` comes back empty only with Always Allow.

## Limits

- Most users never change "Paste from Other Apps", so for them the launch check does nothing. A copy left behind by a crash or `kill -9` stays on the clipboard until something else is copied. It is still concealed, transient and kept to this Mac, so a clipboard manager that honours the markers doesn't store it. "How to check by hand" says what the relaunch check shows under each setting.
- The marker type is the only sign of ownership a new launch has, because nothing keeps the generation of an earlier run's write. Any app can put an item with that type on the clipboard, and with Always Allow a launch clears it. That costs the other app the item it labelled as ours. Keeping the last generation on disk would close this and would also let the check work without the marker; it would add state to the app's data folder and is not part of this step.
- Copying by hand out of the entry editor's unprotected fields goes around the service, as described under "The one path". Notes in particular sometimes hold things people would call secret. Whether the clipboard rule covers those copies is open. Bringing them under it means changing the editor's text fields in `src/ui/legacy/screens/` or `src/ui/widgets/secret_input.rs`, and every such hand copy would then be concealed and cleared after the timer. This step leaves the editor alone.
- On platforms other than macOS the service falls back to GPUI's plain clipboard, as the main window did before. CI only builds for macOS, so that branch is not compiled there.
- `private_pasteboard_reports_always_allow` relies on Apple's documented behaviour that every pasteboard except the general one always allows access.
- `lock_clears_clipboard_ownership` builds the real `AppShell` and reads the real `settings.json`, and the lock and `quit_clears_only_unchanged_own_copy` empty the per-user launch folder, as `automatic_lock_discards_the_draft_and_says_so` already does. No test touches the general pasteboard.
